# 答辩准备

## 一、代码讲解顺序

建议按一次真实请求的顺序讲：

1. `index.html` → `ShopController.home` → `ProductService` → `ProductRepository.search`
2. 注册登录：`AuthController` → `UserService` → `UserRepository` → `ShopUserDetailsService` → `SecurityConfig`
3. 购物车：`CartController` → `CartService` → `CartRepository`
4. 下单：`OrderController.checkout` → `OrderService.checkout` → `OrderRepository` → `ProductRepository.decreaseStock`
5. 订单状态：`OrderController.pay/cancel/complete` → `OrderService` → `OrderRepository`
6. 后台：`AdminController.ship` → `MailService` → `MailRepository`
7. 统计：`AdminStatsController` → `StatsService` → `StatsRepository`

## 二、核心问题与回答

### 1. 为什么选 Spring Boot + Thymeleaf + Spring JDBC？

服务端渲染部署简单，一个 JAR 就能运行；Thymeleaf 页面和 Controller 的对应关系清晰；Spring JDBC 的 SQL 全部显式可见，方便讲清事务、条件更新和统计查询，也避免在答辩时被框架封装挡住细节。

### 2. 一次请求经过哪些层？

浏览器 → Tomcat → Spring Security 过滤器 → Controller → Service → Repository → MySQL。Controller 负责参数和页面，Service 负责业务规则和事务，Repository 只写 SQL。

### 3. 为什么金额用整数“分”？

浮点数累加会出现精度误差。数据库中价格、订单金额、明细单价都用整数分，展示时再除以 100。服务端计算总价，不接收前端传入的金额。

### 4. 六张表的关系？

`shop_user` 一对多 `orders`；`orders` 一对多 `order_item`；`shop_user` 和 `product` 通过 `cart_item` 多对多；`orders` 一对多 `mail_outbox`。`order_item` 同时关联订单和商品，但保存商品名和单价快照。

### 5. 注册如何防止重复邮箱和明文密码？

邮箱统一 `strip + 小写`，数据库有唯一约束，Service 先查重；密码用 `PasswordEncoder`（BCrypt）加盐哈希后入库，数据库只存哈希。

### 6. 登录和 Session 怎么工作？

`ShopUserDetailsService` 按邮箱加载用户和 BCrypt 哈希，Spring Security 校验密码；成功后把认证信息写入 Session，浏览器持有 `JSESSIONID`。登录时会更换 Session，防止会话固定。

### 7. CSRF 在哪里生效？

Spring Security 默认开启 CSRF。Thymeleaf 的 `th:action` 表单会自动带隐藏的 `_csrf` 字段；POST 请求缺少或错误时返回 403。

### 8. 为什么退出用 POST？

GET 退出可能被第三方页面诱导触发。退出会改变状态，所以用 POST + CSRF 保护。

### 9. 商品搜索如何避免 SQL 注入？

所有用户输入都用 `?` 占位符传给 `JdbcTemplate`，不拼接 SQL 字符串。关键词和分类条件通过可选条件 SQL 实现。

### 10. 购物车为什么用联合主键？

`(user_id, product_id)` 联合主键保证同一用户对同一本书只有一行，数量累加即可，天然避免重复条目。

### 11. 下单事务的步骤？

锁定用户行 → 读取购物车 → 逐项校验在售和库存 → 条件扣库存 → 服务端计算总价 → 写 `orders` → 写 `order_item` 快照 → 清空购物车。方法上的 `@Transactional` 保证任一步失败全部回滚。

### 12. 如何防止超卖？

扣库存使用：

```sql
UPDATE product SET stock = stock - ?
WHERE id = ? AND active = 1 AND stock >= ?
```

影响行数为 1 才成功；为 0 说明库存不足，抛异常回滚。两个请求同时抢最后一件时，只有一个能更新成功。

### 13. 为什么下单前锁定用户行？

`SELECT id FROM shop_user WHERE id = ? FOR UPDATE` 把同一用户的下单请求串行化。第二个请求拿到锁时购物车已经清空，避免重复下单。

### 14. 第二件商品库存不足会怎样？

第一件已经扣减，但异常会触发事务回滚，第一件的库存恢复，订单和明细都不会写入。

### 15. 为什么订单明细要存快照？

商品以后可能改名、调价或下架。`order_item` 保存下单时的商品名和单价，历史订单金额不会变。

### 16. 订单状态机如何防止非法流转？

每个 UPDATE 都带当前状态条件，例如：

```sql
UPDATE orders SET status = 'CANCELLED'
WHERE id = ? AND user_id = ? AND status = 'UNPAID'
```

影响 0 行就拒绝。这样不能跳过付款直接发货，也不能重复取消或重复付款。

### 17. 取消订单如何恢复库存且不重复？

先执行带 `status = 'UNPAID'` 条件的 UPDATE；只有影响 1 行才继续恢复库存。重复取消时第二次影响 0 行，不会重复加库存。整个过程在事务内。

### 18. 为什么发货邮件不在事务里发？

SMTP 是外部网络，可能慢或失败。如果邮件发出后事务回滚，会通知顾客一个不存在的发货。因此事务内只写 `mail_outbox`，事务提交后再发送。

### 19. 邮件重试如何避免重复发送？

发送前用条件 UPDATE 把状态从 `PENDING` / `FAILED` / `SAVED` 改成 `SENDING`，只有一个请求能领取成功；发送成功后改为 `SENT` 或 `SAVED`，失败改为 `FAILED` 并记录异常类型。

### 20. 统计口径和 SQL 怎么算？

只统计 `PAID`、`SHIPPED`、`COMPLETED`。汇总用 `COUNT` 和 `SUM(total_cents)`；每日趋势按 `DATE(paid_at)` 分组；商品排行和分类销售额从 `order_item` 的成交快照汇总；Service 补齐最近 30 天没有销售的日期。

### 21. 如何防止越权？

订单查询和状态修改都带 `user_id` 条件；管理员路径由 Spring Security 限制为 `ADMIN`；商品管理、订单管理、报表都在 `/admin/**` 下。仅隐藏页面按钮不算权限控制。

### 22. 已知不足？

付款是模拟的；Session 存在内存中，重启需要重新登录；商品列表未分页；商品图片未实现；真实 SMTP 需要部署环境配置授权码。

## 三、答辩时的注意事项

- 不要声称实现了没做的功能（真实支付、分页、图片上传）。
- 不要把“AI 写的”当作解释；用业务语言讲清为什么这样做。
- 遇到不会的问题，先说思路，再说明当前实现的边界。
- 主动说明已知不足和改进方向，比强行辩解更好。
- 演示前确认 MySQL 已启动、测试账号可登录、管理端有已付款订单可发货。
